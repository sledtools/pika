Chat Server Multi-Device Linking

This is the proposed UX and protocol shape for adding a new device in the server-ordered MLS design. It assumes one room authority per server, per-device MLS leaves, and Nostr only as the identity root plus a backup discovery channel.

Core Model

Each physical device is its own MLS leaf. A user with one npub may appear as multiple leaves in the same room.

Authority

Each room has one chat server that orders commits and messages for that room. There is no cross-server ordering.

Discovery

New devices learn the server list from an existing device first, then from an encrypted self-authored Nostr manifest, then manual entry.

Recovery

If all devices are lost, identity can survive, but room state usually does not. Rejoin is a fresh device-add, not magical recovery.

1. How The New Device Finds Servers

  1. The best path is a local pair with an existing device. That device already knows which chat servers matter.
  2. If no device is available, the fresh device reads an encrypted Nostr event that stores the account's current server list.
  3. Each discovered server is probed with signed login. The server then tells the device which rooms this npub is known to belong to on that server.
  4. The discovery artifact only needs to answer “which servers do I use?”, not “what is every room I am in?”.

Nostr is a backup directory here, not the coordination layer for private chat.

2. Happy Path: Add A New Device

  1. User opens Add Existing Account on the new device.
  2. User approves the link on an existing device and transfers account access plus the current server list over a local authenticated channel.
  3. The new device logs into each server, creates a fresh device_id, and uploads fresh KeyPackages.
  4. The existing device still has valid MLS room state, so it creates the actual add-device commits room by room.
  5. Each room server assigns canonical ordering, persists the commit, and exposes the resulting Welcome.
  6. The new device syncs those Welcomes, joins each room, and starts normal ordered sync from the room server.

Linking can take a while. That is acceptable. The UI should show progress like “37 of 100 rooms ready”.

3. What Happens With 100 Rooms On 10 Servers

This does not create a distributed consensus problem. It creates a fanout job. Each server is independent, and each room is still ordered only by its own authority server.

  • The new device registers once per server, not once per room.
  • The existing device still has to create one MLS add-device commit per room.
  • Those operations can run in parallel by server, with retries and backoff.
  • The UX cost grows with the number of rooms and servers, but the protocol remains understandable.

4. Partial Failure And Resume

If one server is down, rooms on the healthy servers can still finish linking. The user gets partial readiness instead of global failure.

  • Healthy servers complete and expose Welcomes immediately.
  • Broken servers stay pending and keep retrying.
  • The new device should surface a resumable queue, not an all-or-nothing spinner.

5. If All Devices Are Lost

This is a different problem from linking. In a per-device MLS model, a fresh device is a new client. It can recover identity and server discovery, but it usually cannot recover old MLS room state without a surviving device or a separate backup product.

  1. User restores the account identity key on a fresh device.
  2. The fresh device discovers candidate servers from the encrypted Nostr manifest.
  3. Servers can confirm that the account exists, but they cannot manufacture local MLS state for the lost devices.
  4. Other members re-add the recovered device to rooms.
  5. The recovered device gets new Welcomes and continues from the rejoin point forward.

This means total device loss can legitimately lose old room state and some history. That is the intended simplification if we avoid encrypted backups.

6. UX The User Actually Sees

Stage User View What Is Really Happening
Start “Add existing account” New device prepares fresh local storage and waits for local pairing or identity restore.
Pair Scan QR / approve from old device Existing device transfers the server list and enough account material to let the new device authenticate.
Register “Connecting to 10 servers” New device logs in everywhere, registers a new device_id, and uploads KeyPackages.
Enroll “Joining 100 rooms” Existing device creates add-device commits per room and sends them to the correct authority server.
Ready Rooms become available progressively Each room becomes usable as soon as its Welcome has been accepted and ordered sync catches up.
Failure “58 rooms ready, 42 still pending” Some servers or rooms are still retrying. Healthy rooms should remain usable.
